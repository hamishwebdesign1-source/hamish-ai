# Content Factory: Plan

Status: **The full pipeline has now generated a real video end to end, 2026-08-12.** Idea → research → script → video prompt → ViewMax submission → poll → Supabase Storage → quality check → AI caption — all of it, for real, in under a minute, landing on the review screen with a real playable video and a genuinely good AI-written title/caption/hashtags. This followed the ViewMax plan being corrected (Hamish had accidentally subscribed on `viewmax.io`, an unrelated product with no API — the pipeline integrates with `viewmax.studio` specifically) and one more real bug found and fixed via the first paid submission (see "ViewMax task-polling bug" below). Real videos still came back rushed/incomplete though — the script and prompt generation were built around fitting narration into pre-picked cheap durations instead of the reverse; that's now redesigned narration-first (see "Narration-first script/prompt redesign" below), verified against a real Anthropic call, not yet run through an actual paid ViewMax generation. Everything in this doc describes the MVP scope: Idea Discovery → Research → Scoring → Script → ViewMax video → Human Approval, plus YouTube publishing (brought forward from Phase 2). Performance analytics, the AI learning loop, content-fatigue/series detection, and autonomous mode remain out of scope — see "Phase 2" at the bottom.

## Narration-first script/prompt redesign (2026-08-12)

Real generated videos kept coming back "rushed", with incomplete sentences and narration crammed into whatever duration ViewMax's pricing tiers made cheapest — because that's literally what the pipeline was doing: `generate-content-scripts.ts` asked the model to write narration to fit a pre-picked 8-12s or 20-30s tier, and `generate-video-prompt.ts` summed the model's own guessed per-scene durations and snapped the result to whichever tier was nearest. Backwards — the duration should come from the narration, not the other way round.

Rebuilt both files around **narration → duration → scenes → visuals → captions**:
- `generate-content-scripts.ts` now asks for complete, natural narration first, with no duration target at all. Scenes carry a verbatim `narration_segment` (all segments concatenate back to the full narration) instead of an AI-guessed `duration_s`. Real target duration is computed server-side from actual word count at 130 wpm (matches the brief's own worked examples: 75w→~35s, 100w→~46s, 125w→~58s), and each scene's duration is allocated proportionally to its real share of the narration — never guessed. A defensive merge folds any scene that would round under 3s into its neighbour. A one-shot "tighten" pass (real second Claude call, only on the auto-selected winner) rewrites narration shorter — never truncates — if it comes back over ~170 words. Added `character_consistency` (a fixed physical description for any recurring person, applied to every scene's visual). Migration: `supabase/migrations/2026-08-12-content-scripts-character-consistency.sql`.
- `generate-video-prompt.ts` now assembles the ViewMax prompt deterministically from the script's own real narration/scenes rather than asking Claude to write one dense free-text paragraph from scratch — the AI call here is scoped down to just visual style + per-scene camera/lighting direction + editing notes. Output is a labelled template (VOICEOVER / NARRATION / TARGET DURATION / VISUAL STYLE / SCENE 1.. / EDITING / CHARACTER CONSISTENCY / VOICEOVER PRIORITY). Real, hard constraint: ViewMax's `prompt` field caps at 2000 chars, and a fully-detailed template with per-scene narration quotes routinely ran ~2700 chars — solved with a cascading trim (drop redundant per-scene narration quotes since NARRATION already has the full text → proportionally shrink visual-style/editing/per-scene visual text) that is structurally incapable of touching the narration itself, tested against a real 6-scene/58s script.
- Also fixed a gap the redesign would otherwise have reintroduced: hand-editing a script's text (`editContentScript`) previously left `scene_breakdown` stale against the new wording. It now re-slices the edited narration across the existing scenes (`reallocateScenesForEditedNarration`) so duration/segments stay honest after a manual edit.
- Verified against a real Anthropic call on the actual "Victorian doctor" idea (`scripts/test-narration-redesign.ts`, kept in-repo as a reusable check): 79-word narration → 36s target, 5 scenes each holding 6-8s covering a full sentence or more, narration fully intact and unshortened in the final 1995-char ViewMax prompt, `character_consistency` correctly populated for the recurring doctor character.

## Model-selection duration bug — found showing Hamish a real video (2026-08-13)

Asked to show a real video from the narration-first redesign, and it came back exactly the old "rushed" way — 0:08 for a script targeting 20s+. Root cause was in `viewmax.ts`, not the redesign: `pickCheapestVideoOption()` treated fixed-duration models (Veo 3.1 family — `durations: []`, one flat `per_generation` rate, no duration parameter to pass) as if they always "met" whatever target duration was asked for, because there was no `durations` array to check against. Since `PREFERRED_MODELS = ["veo-3-1-fast"]` and veo-3-1-fast's real output is a fixed ~8s (confirmed repeatedly via `quality_flags`), **every submission with a target above ~8s was silently landing on an 8s video regardless of what the script actually needed** — a bug that predates and was completely independent of today's narration/duration redesign, but would have quietly defeated it.

Two real bugs, both fixed:
1. Added `KNOWN_FIXED_DURATIONS_S` (empirically observed real output length per fixed-duration model) — a fixed-duration model now only counts as "meeting the target" if its known real length is actually long enough, never assumed.
2. The last-resort "nothing meets the target anywhere, pick the longest available" fallback had the same class of bug one level down: it reused the cheapest-wins search logic, so among all models' "longest available" offerings it still picked whichever was *cheapest* (veo-3-1-fast, being cheap, kept winning) rather than whichever ran *longest*. Replaced with a dedicated `longestAvailable()` search that compares by real duration first, cost only as a tie-breaker.

Reordered priority: preferred-model duration-adequacy no longer beats a non-preferred model that actually reaches the target — a rushed "trusted" video is a worse result than a full-length one from a lower-trust model, which is the entire point of the narration-first work this bug was undermining. Verified against the live model catalog: a 36s target now correctly selects `grok-imagine-1-5` at a real 30s/90 credits instead of `veo-3-1-fast`'s fixed 8s/30 credits. Trade-off worth flagging: grok-imagine-1-5 was the model Hamish previously called "rushed, unfinished, clearly AI" in earlier testing — that complaint may have been more about duration mismatch than raw output quality (it's now getting a real 30s to work with instead of 10s), but it hasn't been re-verified on rendering quality alone since; watch the next few real approvals.

## ViewMax task-polling bug — found via the first real submission

`submitVideoGeneration()`'s response-parsing was wrong: ViewMax's `POST /api/v1/videos` response has two different ID-shaped fields — a top-level `id` (UUID) and a nested `taskId` (an internal reference to whichever upstream provider, e.g. Kie, actually renders the video) — and they are **not interchangeable**. The original code preferred `taskId`, which meant `GET /api/v1/tasks/{id}` returned `"task not found"` for every real submission, even seconds after a genuine, successfully-charged job. Found by submitting a real job, watching it "process" forever, then manually querying every ID-shaped field in the raw response until one worked. Fixed: `id` is now the only field trusted for polling.

One real submission was charged (10 credits) before the fix and is genuinely untrackable via our API now — marked `needs_review` in `content_videos` with a clear explanation rather than left silently spinning. The very next submission, through the same "Retry submission" button after the fix deployed, completed successfully — see the full trace above.

**Also corrected**: the £15/200-credit figure quoted earlier was wrong — Hamish had briefly (accidentally) subscribed on `viewmax.io`, a completely unrelated product (different company, no public API) before subscribing correctly on `viewmax.studio` (Lite tier, $19/mo, 1,300 credits/month). `VIEWMAX_MONTHLY_CREDIT_BUDGET`'s default moved from 200 to 1200 to match.

## ViewMax integration — findings from a real key (2026-08-12)

Once a real `VIEWMAX_API_KEY` was available, two things built against guessed/defensive field names turned out to need fixing:

1. **`GET /api/v1/credits`'s real field is `remainingCredits`, not `credits`** — the original guess was wrong; `getViewMaxCredits()` now checks both, but the real one confirmed working.
2. **Models don't accept free-form duration/resolution/aspect_ratio.** The real model catalog (`GET /api/v1/models?type=video`, 20 models) shows each model exposes an exact enumerated list of durations/resolutions/aspect_ratios per mode (`text-to-video`, `image-to-video`, ...), plus a cost table keyed by those same values (either a flat `credits[resolution][duration]` grid or a `credits_per_second[resolution]` rate) — there is no arbitrary value. The original `submitReadyIdeas()` just sent `models[0].id` with the AI-generated `video_prompt.duration_s`/`resolution` straight through, which would have been rejected outright. Replaced with `pickCheapestVideoOption()` in `viewmax.ts`, which finds the cheapest (model, duration, resolution) combination that actually supports the idea's target duration and aspect ratio — real prices range from ~13 credits (cheapest model, shortest 9:16 clip) into the hundreds for premium models (Seedance 2.0, Veo, etc.).
   - **A second bug caught during this same pass**: the first version of the duration-matching logic fell back to a model's *longest* available duration whenever the target exceeded it — including when that "longest" was still *shorter* than the target. Since short-duration models tend to be the cheapest in the catalog, "pick cheapest" was silently picking videos half the requested length. Fixed with a two-pass selection: first pass only considers models that can meet-or-exceed the target duration; only if literally nothing can reaches it does it fall back to the closest available (a disclosed compromise, not a silent one).

The credit-buffer check (`VIEWMAX_MIN_CREDIT_BUFFER`) moved from a single flat account-wide threshold checked once per batch to a per-idea check against that idea's actual chosen-option cost (`content-video-pipeline.ts`'s `submitIdeaForVideo`) — a flat threshold said nothing about whether any specific idea's video was actually affordable once real per-model pricing was known.

**Current blocker: credits.** The account has 10 credits; the cheapest real video found across all 20 models for a typical 15-30s 9:16 script costs more than that. No video will be generated until credits are topped up at [viewmax.studio/pricing](https://viewmax.studio/pricing).

## Cost-effectiveness fix (2026-08-12) — Hamish's real plan: £15/mo, 200 ViewMax credits

Pulled the exact cost table for every duration ViewMax offers at 9:16 and found a hard cliff: the cheapest real per-video cost is **~15-21 credits at 12 seconds or under** (`seedance-1-5-pro`, 480p — 7cr@4s, 15cr@8s, 21cr@12s), but the moment a script runs even 1 second past the ~15s mark, the cheapest available option jumps to a **flat 60 credits** (most affordable models skip straight from a ~15s tier to 30s — there's no 16-29s option at any price). Going from 12s to 16s doesn't cost a bit more, it costs **3x more**, for 4 extra seconds nobody asked for.

The pipeline's own script-generation prompt was the actual cause: it told the model to write scenes summing to "15-40 seconds," landing squarely in the expensive zone almost every time. Fixed at the source, not just papered over downstream:

- `generate-content-scripts.ts`'s prompt now requires scenes to sum to **12 seconds or less**, explained to the model as a real cost constraint of the platform, not a stylistic note.
- `generate-video-prompt.ts` clamps the computed duration to **8-12s** (`MIN_DURATION_S`/`MAX_DURATION_S`) as a backstop, in case a script variant still comes back longer.
- **A monthly spend cap**, not just a per-video affordability check: `content-video-pipeline.ts`'s `submitIdeaForVideo` now checks this calendar month's total ViewMax spend (summed from `content_ai_usage`) against `VIEWMAX_MONTHLY_CREDIT_BUDGET` (defaults to 200, matching the real plan) before submitting anything — independent of whatever the live account balance happens to be. Without this, a burst of 3 ready ideas on day one (the old `MAX_SUBMISSIONS_PER_RUN`) could spend a third of the whole month's budget immediately, then go quiet for weeks.
- `MAX_SUBMISSIONS_PER_RUN` dropped from 3 to **1** — paces submissions to roughly one a day rather than bursts, so the monthly budget actually gets spread across the month instead of front-loaded.

**Real economics with these fixes**: at ≤12s and the cheapest viable model, ~15-21 credits/video → **200 credits ≈ 9-13 videos/month**, roughly one every 2-3 days, at ~£1.15-£1.65/video for generation. Before the fix, undisciplined durations would have averaged ~60 credits/video → only 3/month at ~£5/video, for barely longer clips. Short-form hooks work fine at 8-12s anyway — this isn't really a creative compromise, ViewMax's pricing just happens to reward the same tight pacing that makes for a good hook in the first place.

**A deliberate change from the original plan, confirmed with Hamish**: there is no mandatory "pick one of three scripts" human gate. `generate-content-scripts.ts` scores all three variants itself and auto-selects the strongest, auto-chaining straight into video-prompt generation — Hamish reviews/overrides at his discretion (`selectContentScript`/`editContentScript`), but the pipeline never blocks waiting for that. The only two things that ever require deliberate human action are rejecting an idea and the eventual video approval (Phase D).

## Phase B — built, not yet live (scripts, auto-selection, video prompt)

Built: `content_scripts` table (`supabase/schema-content-scripts.sql` — hook/beats/scene_breakdown/style/score, not a flat `script_body` blob, so the review UI can show the actual Hook/Setup/Escalation/Payoff/Ending retention structure the brief's Script Engine section asks for), `generate-content-scripts.ts` (one call, 3 variants — curiosity/shock/story — each self-scored 0-10 by the model, highest score auto-selected), `generate-video-prompt.ts` (separate small call turning the selected script into a ViewMax-ready prompt — kept separate from script generation for the same schema-size reliability reason `research-lead.ts` splits its two large tool calls; aspect ratio/duration computed deterministically, not asked of the model). `research-content-idea.ts` now chains straight into `generateContentScripts()` for any idea that clears the score gate, same best-effort chaining shape as discovery→research. `/admin/content-factory/[id]/page.tsx` gained a Script section (`ContentScriptPanel`) showing the selected script, its scene breakdown, the generated video prompt, a Regenerate action (asks for confirmation if it would clobber a hand-edit), and a collapsed "other variants" panel with a manual override per variant. Still zero ViewMax cost — this phase only produces the prompt ViewMax would eventually receive, never calls ViewMax itself.

**Two real reliability bugs found via live testing and fixed** (both in `research-content-idea.ts`, both the same root cause: Haiku not strictly honouring the JSON schema despite `enum`/`type: array` being declared):
1. The four novelty/competition/production/evergreen band fields came back as hedged phrases ("medium-to-high (the general concept is old; but this specific case is genuinely underexplored)") instead of a bare `low`/`medium`/`high` word. A strict `===` comparison against the enum silently treated every non-exact match as the lowest band, so **every idea scored 0 regardless of actual quality** — a correctness bug that would have killed the pipeline outright. Fixed with `normaliseBand()` (parses out the last mentioned band word, defaults to `medium` rather than the worst case if nothing parses) plus tightened prompt/schema wording as defense in depth.
2. `competitor_examples` (declared as `array of string`) came back as a single plain-text string on one real response, crashing `ContentIdeaResearchButton`'s `.map()` at render time with data that had already been saved. Fixed with a forgiving `toStringArray()` coercion (wraps a lone string as a single-element array instead of discarding it) applied before anything is saved.

Neither bug affects `generate-content-scripts.ts`/`generate-video-prompt.ts` the same way — both of those already call `.map()`/string methods on their own AI output *before* saving, so an equivalent shape mismatch there degrades to a caught generation failure (logged, swallowed, idea stays at its current status) rather than corrupting saved data that later crashes a render.

**Live-verified end to end, 2026-08-11, `schema-content-scripts.sql` applied**: re-ran research on the Victorian-doctor idea and watched the full autonomous chain complete for real — `researched` (score 4/5) → `script_review` (3 real variants: curiosity 8.5/10, shock 7.5/10, story 8/10, curiosity auto-selected) → `ready_for_video`, with a genuinely strong, detailed ViewMax-ready prompt (19s, 9:16, scene-by-scene camera/lighting/transition direction) generated for the selected script. The full detail page rendered correctly — research findings, score breakdown, selected script, scene breakdown, video prompt panel — with zero console errors. One caveat: the "Show other variants" collapse toggle couldn't be click-verified in this session's browser tooling (a stated environment limitation, not a data/logic issue — confirmed by code review: it's the identical `useState` toggle pattern already used successfully by `ContentIdeaResearchButton`), worth a real click-through next time the admin UI is open normally.

## Phase C — built, not yet live (Storage + ViewMax)

Built: `schema-content-storage.sql` (private `content-videos` bucket), `schema-content-videos.sql`, `schema-content-usage.sql` (`content_ai_usage`, the only cost-tracking table — deliberately minimal, not a billing system) — **run content-videos.sql before content-usage.sql**, the latter has a foreign key onto the former. `src/lib/viewmax.ts` (client for ViewMax's v1 REST API — base URL, auth header, the `{code,message,data}` envelope, and the five error codes are confirmed from their public docs; the exact result-URL field name on a real task response is not independently confirmed — no ViewMax account exists yet — so it's checked defensively against three possible shapes and should be simplified once a real response is seen). `content-video-storage.ts` (first Supabase Storage usage in this codebase), `content-ai-usage.ts` (now wired into every Haiku call site from Phase A/B retroactively, plus every ViewMax call). `content-video-pipeline.ts` (`submitReadyIdeas()` + `pollInFlightVideos()`), `content-quality-check.ts` (pure heuristic, no AI call), `generate-content-copy.ts` (title/caption/hashtags). `content-video-pipeline` cron (every 5 minutes). `send-content-alert.ts` (consolidated per-run email, built alongside Phase C rather than deferred to D since the cron needed it immediately). A "Video generation" status panel + manual retry action on `[id]/page.tsx`, and a ViewMax connection/credits indicator on the list page.

**Poll-interval decision:** ViewMax's docs say poll every 5s; a multi-minute generation can't be tracked by one Vercel invocation and this codebase deliberately has no persistent job queue. The `content-video-pipeline` cron runs every 5 minutes and does a bounded inline poll burst (up to 6 polls, 5s apart, ~30s) per in-flight video, then leaves it for the next tick if still not done — a video appears in the review queue within ~5 minutes of finishing, not 5 seconds, which is fine for a human-reviewed internal tool. Needs confirming Hamish's Vercel plan supports 5-minute cron granularity before this ships.

**State-modeling note:** a hard submission or generation failure sets the idea to `status: 'failed'`, not `'video_review'` — `'video_review'` is reserved for outcomes a human genuinely needs to look at (a succeeded video, or an ambiguous ViewMax-said-success-but-something-else-broke case), not a clean failure with nothing to review.

**No ViewMax account exists yet** (confirmed with Hamish) — this phase deploys safely with `VIEWMAX_API_KEY` unset (the pipeline logs "not configured" and skips, everything else keeps working) and only starts actually generating video once he signs up at viewmax.studio and the key is added. **Live-verified 2026-08-11/12**: with the key unset, `/admin/content-factory` correctly shows a "ViewMax isn't connected yet" banner and a `—` credits tile, `checkViewMaxConnection()` returns the right reason, and an idea already sitting at `ready_for_video` from Phase B testing rendered with no crash and no `content_videos` row (exactly the expected no-op). `tsc --noEmit` and `npm run lint` are both clean (zero new issues). `npm run build` could not be verified in this session — it failed on an unrelated, pre-existing Google Fonts network-fetch error in `src/app/concepts/mchale-builders/page.tsx` (a file untouched by this work), consistent with a sandboxed-environment network restriction rather than a code defect; worth a real `npm run build` once network access to fonts.googleapis.com is available.

## YouTube publishing — brought forward from Phase 2 (2026-08-12)

Built on request, ahead of the original phase order: a real "Upload to YouTube" button on the approval screen, shown once a video is approved.

- `supabase/schema-platform-posts.sql` — `platform_posts` (one row per publish attempt; `platform` is already multi-valued so TikTok can join this same table later without a schema change). Not yet applied — paste before this does anything.
- `src/lib/youtube.ts` — `uploadVideoToYouTube()` (fetches the video's bytes, calls `youtube.videos.insert` with the AI-drafted title/caption/hashtags as metadata) and `checkYouTubeConnection()`. Reuses the *same* shared Google OAuth2 client every other Google integration in this codebase uses (`google-auth.ts`) — one refresh token now covers Gmail + Calendar + YouTube, not a separate connector.
- `google-setup/page.tsx`'s `SCOPES` gained `youtube.upload`. **An account connected before this scope existed needs one manual reconnect** at `/admin/google-setup` — Google only re-issues the full scope set on a fresh consent, not incrementally, so the existing Gmail/Calendar connection alone won't cover YouTube uploads.
- `publishVideoToYouTube()` in `admin/actions.ts` — one server action does the whole job (download from Supabase Storage → upload to YouTube → record the result), same "one click, no manual steps" shape as everything else in this pipeline. Never throws; a failed upload leaves a `platform_posts` row with `status='failed'` and the real error.
- `ContentVideoDecided` (the approval screen) grew a `YouTubePublishPanel` — a privacy-status picker (private/unlisted/public, defaults to private) plus the upload button, shown only once a video is approved and kept as a deliberate second step rather than bundled into the Approve click itself.
- `content.youtube_published`/`content.youtube_publish_failed` are audit-log-only (human-triggered publish, not AI activity) — same convention as `content.video_approved`/`rejected`, not added to `AI_ACTIVITY_ACTIONS`.

**Not yet live-tested** — no real video exists yet (ViewMax credits still pending), so the upload path is code-complete and typechecked but unexercised against a real file. Verify end to end once a real approved video exists: reconnect Google for the new scope, paste the SQL, click Upload.
